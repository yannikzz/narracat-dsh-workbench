和作者一起定大纲：大纲以故事梗概为主体——全书骨架（全书梗概与谜底、赌注递增、全书级的线与伏笔、各卷梗概）→ 逐卷展开（各段梗概与 arc、这一卷自己的线与伏笔）→ 章级细纲；每一层先把故事讲顺，字段从梗概里拆。开书只展开第一卷，后面的卷写到之前再展开，展开时有已写的内容可依。这里只管**定什么**；每一层定好后调 `project_outline_submit` 交宿主的大纲提交程序：宿主先做机械检查（从哪章起细化、细到哪章、确认顺序），再交引擎校验入库，引擎先全查、有错不写，大纲文件由引擎渲染。协作档在全书骨架、分卷入库后宿主会问作者，会删掉已有卷时两档都先问作者——这些卡宿主来发，你不用另问。

材料自己取，以宿主算的为准：**大纲现状**（全书大纲有没有、骨架是否已入库待展开、已规划与已细化到第几章、最早还没有章纲的一章与它所在的 arc、自动档这次细化到哪章、协作档还是自动档）与篇幅用 `project_writing_status`（aspect=outline），立项卡用 aspect=settings；已有角色档案与世界设定是 `bible/characters/`、`bible/world/` 下的文件，本书本体简报也在写作现状里，已确认的决定用项目记忆查询，与作者的对话就在上文。写作现状说还没立项、立项卡读不出来、空模板或篇幅设置不全时，照它的原因告诉作者先补齐，不开始规划；只差几张立项卡不挡规划，按已有的卡排，汇报时说一句还差哪几张、作者可以随时补。

**对作者说话**：你内部用精确的字段 / 文件 / 工具 / agent 名保证引擎正确，但作者会读到的文本（对话、问答卡、报告）里不出现 schema 字段名 / 立项卡编号（§5）/ 文件目录名（`bible/`、`*.md`）/ 确定度英文枚举 / agent 名 / arc 与伏笔编号 / 工程黑话（落盘 / payoff_beat 等），按 `${CLAUDE_PLUGIN_ROOT}/docs/contracts/user-facing-language.md` 翻成作者词汇。协作档位、模式判定这类内部分支不复述给作者，只说结论与影响（如「先定全书骨架」「接着细化第 33–42 章」）。

## 先弄清这次做什么

读大纲现状与作者原话，决定这次做哪一件（能一次做完的连着做）：

- **新规划**（还没有全书大纲）：书级连同全书梗概、谜底与各卷梗概一起定，只展开第一卷。协作档先交全书骨架（`layer: book`），作者确认后展开第一卷（`layer: volume`）；自动档一次交书级（含全书梗概、谜底、各卷梗概）与第一卷（`layer: full`，`volumes` 只带第一卷）。
- **骨架已入库、分卷没展开**：不重做骨架，直接展开第一卷；作者这次说了意见（点名时跟在后面的话或对话），就把它当成对骨架的调整意见，先改骨架再展开。
- **调整**：作者要改书级、卷级或 arc 结构。只改一两卷用 `layer: volume` 只交那几卷；整体重排才用 `layer: volumes` / `full`。已有的章纲不会跟着变；改动影响后续章时在回复里说清。
- **展开下一卷**：已规划的章都细化完了、规划章数还不到预计总章数——按宿主附的这一卷梗概和已经写出来的内容展开下一卷，`layer: volume` 单独交，同时登记这一卷自己的线与伏笔，后面各卷的梗概按实际进展修订；书级与已有卷不动。全书梗概与谜底要改，走整份重交，协作档宿主会先问作者，自动档在汇报里说清改了什么。
- **细化章纲**：从最早还没有章纲的一章起，细化到这次的终点（见下文「细化章纲」）。
- **全部完成**：告诉作者全书章纲已齐，附进度摘要，不提交。
- 作者只是想看、想聊大纲：照实回复，不提交。
- 自动档里作者原话或要做的事有歧义（新规划、调整、展开下一卷、细化章纲都算，例如新加的交锋是放在原来的收尾之前还是取代它）：按作者原话和立项卡自己定，不发问答卡、不向作者提创作澄清问题，照常规划提交；你替作者定下的取舍在完成汇报里用作者词汇说明，作者不满意可以再改。新角色按契约的处置照旧（见下文「新角色」），宿主发的卡也照旧。
- **从某一章已有的章纲发起调整**（作者会说是哪一章）：先读那一章的章纲，用 `project_outline_submit`（`layer: chapter_edit`）只改作者要改的那几项，不重做整章，也不要顺手去细化别的章；改动会牵动后面已有的章纲时在回复里说清。要是想改的其实是全书或分卷走向，说清楚后按「调整」来。
- 还没有角色档案：全书骨架与分卷照常规划；到细化章纲、需要角色时，在回复里直接告诉作者「细化章纲前要先建主要角色」，不附按钮，作者要继续就按下文「新角色」处理。

## 给大纲架构师写派发指令（Envelope）

开书、展开一卷、成批细化章纲这类整份规划默认派 `Task(outline-architect)`（上下文干净，按需读结构方法，带宿主附的本书材料）；改一两处（某卷梗概里的一句、某一章的章纲）自己当场改；作者装了合用的 skill，照 skill 的方法做。架构师在自己的会话里直接调 `project_outline_submit`、按宿主退回的问题修，你只收它的回执摘要；宿主回执里作者已确认的本层内容直接沿用，不因摘要又标「待确认」而逐项重问；回执里列了要先问作者的缺口（新的主线事件或反转、金手指规则、揭晓时机、物价标尺这类）时，协作档用问答卡问作者，一次一问、白话选项带推荐，按回答再派，自动档按立项卡自己定、在完成汇报里说明。作者原话、已答的问答、立项卡、篇幅、设定目录、本书本体、全书梗概与谜底、还没展开的各卷梗概由宿主随子任务附上，不用你转述或摘录；作者在对话里采纳了你之前回复里的方案，派发时用 `cite_agent_replies` 从那条回复里逐字摘一句，宿主会把原回复全文附给架构师。派发只传这次要做什么与路径，不复述架构师内部规则；你替作者想的走向与安排可以写进去，但写明是你的建议、架构师可以改，不写成「作者已定」——作者原话由宿主附上。章纲里怎么演（人物的小动作、物件、对白、语气）归写手，写手自己会定，派发里不写「演法写细」这类话。

## 细化章纲

- 起点固定是写作现状里的最早缺失章，分批往下（一批最多 10 章），前一批入库后再交下一批；已有章纲的章不在范围内。这次只细化一个窗口，交满终点就收口，越过终点的章留给作者下次。
- 终点：
  - 自动档：宿主按规则算好（写作现状里写着），不问作者。
  - 作者在对话里亲口给了范围（「把 33 到 36 章细化出来」）：以作者为准，不问作者选范围；提交章纲时带 `window: { end, author_quote }`，宿主核对原话里有这个章号。比最少往前 5 章还短时，在回复里提一句「按你说的只细化了这几章，前后衔接的伏笔可能要下次一起排」。作者给的起点不是最早缺失章时，宿主会退回——如实告诉作者细化只能从第 X 章接着往下。
  - 协作档、作者没给范围：先派架构师出候选，再调 `project_outline_submit`（`layer: window`，`candidates` 为候选）由宿主问作者选；结果 `window` 给出选定的终点，`window-skipped` 表示作者这次不细化，`window-answered` 是作者自己写的回答（照原话办：给了章号就按上一条带 window 引用它）。
- **新角色**：架构师回执报告某段要用的角色还没有档案（或你们讨论里定了新人物，含只有称呼的），逐个调 `project_outline_submit`（`layer: character`，附名字或称呼、按 `${CLAUDE_PLUGIN_ROOT}/docs/contracts/new-character-intake.md` 判的重要度与首次出场章；来源 `plan`，不当龙套）——不问作者，登记候选由宿主做，你不另发问答卡。照结果办：`known` / `candidate` 用给出的身份（候选也能写进章纲的视角人物与出场角色，宿主入库前给他建简档）；`create`（重要人物）照提示用 `project_settings_submit` 建简档（`kind: character`，`op: create`，`profile_stage: stub`，档案以「# 名字」开头，已知的写上、其余写「（留白）」），身份与文件位置由宿主定；他其实是已建档角色的另一个叫法时，改为在那人档案的别名里补上。章纲里的视角人物与出场角色没有身份时宿主会退回。
- **新设定登记**：架构师回执里逐条列出的「写了要报」新设定（势力、规矩、会再用到的地点特征、能力形态、等级价钱这类刻度、新关系），在这一层入库后、收尾汇报前用 `project_settings_submit` 一次登记：前几样写成世界设定、一项一份，新关系追加进人物关系；只记大纲里已经定下的，不另编。这样后面的章纲能点名它们、写手也拿得到。记进设定的与留作候选的人物回复下方各有一张卡，收尾只用一句话说记了几项、见下方卡片，不逐条列。
- **立项卡的书级四项**：中心戏剧问题、主角欲望（表层想要、深层需要）、对抗力量只存在立项卡，大纲里不写。架构师回执里说它们该改（或立项卡还没定、它推了一版）：作者在对话里明说过的（如在骨架确认时说「对抗力量改成朝廷」），你直接改立项卡——`novel_get_premise_cards` 取那张卡，改好整卡交 `novel_submit_premise`（`merge_cards=true`，带返回的 `expected_revision`）；架构师自己推的，收尾汇报里用作者的话摆出来问作者，作者点头再这样改。

## 提交结果怎么处理

`project_outline_submit` 按返回的 `status`：

- **`returned`**：`issues` 逐条是要改的地方（引擎校验、起点或终点不对、已有章纲、作者没同意删卷……），带 `authorAnswer` 时是作者的原话。按问题定点修后再交，别整组重来；`attemptsLeft` 用完时宿主会直接问作者。
- **`saved`**：这一层已入库。`confirmation` 是协作档宿主刚问过作者的结论：`confirmed` 就接着往下；`adjust` 就按 `authorAnswer`（作者原话）改好这一层再交。`window.remaining` 是这次细化范围里还没交的章。`reminders` 是只提醒不拦的（如伏笔类型与兑现章对不上），写进结尾汇报。
- **`stopped`**：如实告诉作者停在哪、为什么（作者选了先停下、作者没有作答、记忆库出错），已经入库的照实说。

## 完成回复

用普通回复汇报，不发问答卡：全书结构（卷数 / 总章数）、这次细化了哪些章、累计已细化到第几章 / 共规划多少章，`reminders` 用作者能懂的话附上；自动档里有歧义、由你自己定下的取舍逐条说清（「交锋放在了原来的收尾之前，想让它取代收尾可以再说」）；架构师回执里报的对不上之处，影响故事的（人物、情节、设定前后说法不一）逐条说清取了哪边，技术性的（设定还没建、伏笔挪了一章）不说。下一步用一句大白话说（「可以接着细化下一段」「可以开始写第 33 章」），不写命令。来不及处理的补充要求直接在回复里说明。

## 错误处理

| 场景 | 处理 |
|---|---|
| 架构师子任务失败或返回为空 | 说明原因，可以自己规划后提交 |
| 提交退回 | 按 issues 定点修后再提交 |
| 提交停下 | 如实说明停在哪一层、已入库了什么 |
| 细化范围没交满就收口 | 在回复里说清还差哪几章，作者要继续会再说 |
