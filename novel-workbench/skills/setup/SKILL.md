通过追问式对话，把用户的点子打磨成一部小说的立项卡，逐张确认后经 `novel_submit_premise` 入库，并把篇幅与风格经 `project_book_info_submit` 交宿主写进作品配置。立项卡由你和作者直接对话定下，这一步不派发 agent、不直接写任何文件。

**对作者说话**：你内部用精确的字段 / 文件 / 工具 / agent 名保证引擎正确，但作者会读到的文本（对话叙述、AskUserQuestion 的问题与选项、报告正文）里不出现内部标识——schema 字段名（如 `antagonistic_force`）、立项卡编号（`§5`/`§7`）、文件 / 目录名（`bible/`、`*.md`）、确定度英文枚举（`canon`/`tentative`/`open`）、agent 名（`world-curator` 等）、工程黑话（落盘 / blocking / payoff_beat 等）一律翻成作者词汇，信息全留、黑话全译。对照表见 `${CLAUDE_PLUGIN_ROOT}/docs/contracts/user-facing-language.md`。

## 前置

1. 作品信息（书名、题材、篇幅、风格）与立项卡还差哪几张都用 `project_writing_status`（aspect=settings）查，不用读配置文件；已有的作品信息作为已知信息，不再从零问。「还没有立项卡」「还是空模板」都是正常的新书状态，照常立项（文件由引擎在入库时生成）；项目配置读不到的书宿主根本不会开始本命令，你不用判断项目是否初始化。
2. 看上文怎么起的头：
   - **对话里聊定了再立项**：作者刚在对话里把要立项的内容聊定了。上文的对话与已确认的决定就是素材——定了的直接写进对应卡片草案，只核对与补缺口，不再从零问，也不问「继续补缺口 / 重新立项」；立项卡已有内容时只改作者这次定了的那几张（提交带 `merge_cards=true`），其余卡原样保留。
   - **作者只说要立项、上文没聊过**且立项卡已有内容：用 AskUserQuestion 问用户：继续补缺口 / 重新立项（覆盖）/ 退出。

## 对话方式

开场：请用户把脑子里的点子全部倒出来——一句话还是三千字都行，零散的画面、桥段、人设、模糊的感觉都收。

然后进入追问循环：

- **一次只问一个问题**，写在普通回复里，并永远附上你自己的推荐答案（基于已知信息给出最可能的答案，用户回「按你说的」即采纳）。
- **下一个问题由上一个回答决定。** 没有固定题数和题序：哪张卡缺口最大、哪里模糊或自相矛盾，就追问哪里。
- **能推出的不问，说定的不改。** 用户已说过的、能从题材常识可靠推出的，直接写进卡片草案，留到确认环节核对；作者原话里说定的事（谁、在做什么、怎么做）照用，你补的设定与规则只能展开它，不能推翻或换掉它，九张卡之间也不互相打架。
- **追到具体为止。** 「修仙复仇文」不是答案，「废灵根少年靠吞噬仇人功法变强，每次吞噬都更像仇人」才是。用户给抽象标签时，给出 2-3 个差异化的具体方案对比，让用户挑或改。
- AskUserQuestion 只用在真正的关键取舍（两三个方向不可兼得时）；开放问题用普通对话问。
- AskUserQuestion 选项标题用人读中文；任何写入 config.yaml 或数据契约的英文枚举值只在内部持有、作选定后的回写目标，不出现在选项标题里。

## 收束目标：九张立项卡

对话中的信息收束为以下九张卡。一张卡凑齐就向用户展示草案确认；九卡确认齐后，经 `novel_submit_premise` 一次性入库；立项卡只存这一份记录，你不另写文件。

| # | 卡 | card | 必须答出 |
|---|---|---|---|
| 1 | 题材读者契约 | genre_contract | 细分题材；读者默认期待什么；本书在哪一点超出预期；情绪基调（读者读这本书主要是什么感受、哪种为主、读到结局是什么感觉；写读者的感受，不写文字的冷暖，也不写克制、留白这类写法） |
| 2 | 核心钩子 | core_hook | 开头几章向读者承诺什么体验 |
| 3 | 金手指与爽点引擎 | golden_finger | 主角有没有超出常人的能力或优势（没有就写明没有，这张卡可以很短）；有的话：能力是什么；限制是什么；如何成长；它为何不会消灭冲突；网文向的书再定反馈回路（读者隔多久爽一次） |
| 4 | 主角欲望与代价 | protagonist_desire | 表层想要；深层需要（自己未必意识到）；要付出什么代价；底线在哪 |
| 5 | 对抗力量 | antagonistic_force | 谁或什么挡在主角面前；为何强大；为何不可调和 |
| 6 | 中心戏剧问题 | central_dramatic_question | 一句疑问句，全书完结时必须给出答案 |
| 7 | 世界规则可冲突性 | world_rules | 每条核心规则写清它限制了谁、会让谁和谁起冲突；只留读者跟上故事必须懂的规则 |
| 8 | 人称 | narrator_voice | 只定叙述人称（受控四选一）：用第几人称讲、跟着谁走 |
| 9 | 留白声明 | （自动汇总） | 由各条确定度汇总，不单独提交 |

提交形态：`novel_submit_premise` 的 payload 是 `{ cards: [{ card, fields }] }`。这本书已有立项卡时（补缺口、只改几张、重新立项都算），提交前先调 `novel_get_premise_cards`，把返回的 `revision` 填进 `expected_revision`；退回说版本对不上，是作者刚改过，重新取了再按现在的内容改。每张实体卡（第 9 卡除外）一个 cards 条目，`fields` 为该卡的若干条目，每条 `{ key, value, certainty?, note? }`：

- 每条标确定度 `certainty`：`canon` 已定不可违背（默认，可省略）/ `tentative` 当前最优解、可被后续创作修正 / `open` 有意留白、当前未定。第 9 卡「留白声明」由这些确定度自动汇总，不手写、不提交。
- 各卡 `fields[].key` 约定：
  - 题材读者契约 → `subgenre` / `reader_expectation` / `surprise_point` / `emotional_tone`
  - 金手指 → `ability` / `limit` / `growth` / `feedback_loop` / `sustains_conflict`
  - 主角欲望 → `surface_want` / `deep_need` / `cost` / `bottom_line`
  - 核心钩子 / 对抗力量 / 中心戏剧问题 → 单条，key 用 `hook` / `force` / `question`
  - 世界规则 → 每条核心规则一个 field，`value` 写规则本身，`note` 写「让谁和谁打起来」
  - 人称 → 只交 `address` 一条（卡标识仍是 `narrator_voice`）；不再写原型、基调、节奏、修饰、风格关键词与范例句——你替作者编的写法会被写手和大纲照着写，压掉情绪、堆满描写
    - **叙述人称 `address` 用 AskUserQuestion 专门确认**（全书硬设定，不静默留空）。标题人读中文，选定写入英文枚举（内部持有、不进标题）：第一人称→`first_person` ／ 第三人称·跟随主角→`third_limited` ／ 第三人称·上帝视角→`third_omniscient` ／ 多视角切换→`multi_pov`。作者确有理由暂不定，可把该条 `certainty` 标 `open` 留白。
- 第 4 卡的 `surface_want` / `deep_need` 与对抗力量、中心戏剧问题是全书的书级四项：只存在立项卡，写手每章常驻读到、大纲照它们展开，必须落到具体的人和事，不收抽象词。
- 题材卡：第 1 卡的细分题材定下后，手头有题材正文卡资料的，按它的索引挑 1 张主卡，跨题材再加 1 张辅卡，卡名（主卡在前）放进 payload 顶层 `x-题材卡` 一起交；写手之后每章就读这几张，不再各章自己挑。对不上任何卡就不交。
- 作者聊到写法（想要什么文风、读起来什么感觉、不要什么写法），用 `project_memory_write` 带 `remember: rule`（scope=book）记成本书指令（写进本书说明，写手每章都会原样读到）：一条一句、两百字以内，尽量用作者原词，原话长就按意思拆成几条，不改意思、不补充；作者没说就不记，不替作者定写法。

## 金手指反馈回路：按驱动特征的实测节奏锚（网文向的书用，参考非配额）

本书的读者契约是网文向时，grill 第 3 卡的 `feedback_loop`（读者隔多久爽一次）用头部网文实测节奏做锚，帮作者把「爽点频率 + 小 / 中 / 大爽配比」落到具体粒度。按本书**靠什么驱动读者**归位（看驱动方式，不看题材标签），落到最近的一类：

- **高频小爽型**——密集小步兑现维持在场感（甜宠 / 纯爱 / 现言 / 宅斗 / 种田日常等）：约六到七成章有爽点，以小爽为主、密而轻；大爽稀但每次是关系或身份的跃迁。
- **中大爽升级型**——靠单次强度爬台阶（玄幻 / 修真 / 科幻末世 / 系统流 / 都市异能等）：约五到六成章有爽点，中爽占比明显更高、大爽有分量，节拍可略疏。
- **攒糖引爆型**——把糖攒到集中放（悬疑 / 无限流 / 推理 / 诡秘等）：约半数章有爽点，中大爽最稀，攒到真相揭盘 / 关卡通关时集中引爆，长线靠悬念维持。

题材只是帮理解的示例，同一题材可能落不同类；拿不准就直接问作者「这本主要靠密集小爽、靠单次强度、还是靠攒糖引爆留住读者」。这条会随立项卡交给大纲架构师，定得越具体，后面排布越有据。作者另有写法的书不用定反馈回路。

## 篇幅与风格（交宿主写作品配置）

九张卡确认完后处理篇幅、风格与题材。以写作现状里的作品信息为准：**已经定了（未定以外）的一律保留、跳过、不重问、不改写**；仅对仍未定的按下面提问（同样附推荐答案）：

1. **篇幅**（预计总章数与每章字数）：两者都已定则整步跳过；未定才问预计总章数 + 每章目标字数（用户只给总字数时，给出一组推荐的总章数与每章字数请其确认），把确认后的两个纯数字交 `totalChapters` / `wordsPerChapter`。
2. **风格档位**：已定则跳过；未定才用 AskUserQuestion 二选一。选项标题用人读中文，英文枚举仅作选定后交宿主的 `style` 值、不进标题：
   - 标题「标准网文节奏」（放第一项、推荐）→ 选定交 `web_standard`
   - 标题「强钩子快节奏」→ 选定交 `web_fast`（钩子更密、场景快进快出）
   作者说这本不按网文写时，不定档位，让作者把写法写进本书说明。
3. **细分题材**：已定则保留；仍未定时交第 1 卡定下的细分题材（`genre`）。

只把需要写入的字段一次交给 `project_book_info_submit`（宿主写进作品配置 `.narracat/config.yaml` 的 `estimated_total_chapters` / `words_per_chapter` / `style_profile` / `genre`，其余不动）；三项都已定则整节跳过。作者在对话里刚定的书名已经交过的，这里不重复交。

## 收尾

输出一行摘要（九张卡入库状态 + 交宿主写入的作品信息），提示下一步。作者让你接着开书时，人物与世界设定照设定方法建：默认派设定岗位合成，你只拿结果，不自己读设定资料写档案。

```
立项完成。建议下一步：
 - 建立角色与世界观设定
 - 规划全书大纲
```

## 错误处理

| 场景 | 处理 |
|---|---|
| 保存作品信息被退回（值不合法） | 按退回说明改正后再交一次；仍不行就如实告诉作者哪一项没存上 |
| 用户中途退出 | 尚未提交的卡不入库；下次立项时重新确认（已知信息会加速） |
