# 契约：大纲规划共享逻辑

> **定位：** 本文件是大纲推进逻辑（细纲状态同步 / earliest-missing 推进 / 叙事断点窗口 / 不覆盖 / 阶段一范围）的语义 SSOT。§1–§3 里确定的部分（已细化与已规划集合、最早缺失章、自动档终点、起点固定、不超过终点、不覆盖、确认顺序、删卷先问作者）**由 App 宿主计算与强制**：宿主把大纲现状写进交接材料，提交时经大纲提交程序（`project_outline_submit`）机械检查；本文件描述语义，宿主实现与本文件保持一致。规则语义变更只改本文件，并同步宿主。

---

## §1 细纲状态同步（文件系统是 SSOT）

已细化章号集合 `C_outlined` 的唯一真值来源是文件系统：

1. 扫描章纲 json `.narracat/data/outline/vol-*/ch-*.json`（章纲只存这一份，作品里没有章纲 md）
2. 从文件名解析章号集合 `C_outlined`（格式 `.narracat/data/outline/vol-{VV}/ch-{NNN}.json`，VV 两位补零卷号、NNN 三位补零章号；解析失败的文件名跳过，不阻断）
3. 不读、不维护任何缓存字段——章纲 json 由章纲提交写入，文件即状态；任何中断后重跑，本扫描自动得到正确状态（idempotent 自愈）

计算方：App 宿主（大纲运行准备时写进交接材料，每次章纲提交前后重算）。`/narracat:write` 入口对单章细纲的存在性检查与本节同源（直接查文件）。

## §2 earliest-missing 与叙事断点窗口

**前置：** 阶段一已提交（`project_outline_submit` 已写入全书大纲结构文件并入库 arc / storylines / 伏笔注册表）；已按 §1 得 `C_outlined`。

**定义：**

- `C_planned` = 全书大纲已展开各卷覆盖的章号集合：从 1 到已展开各卷 arc 的最后一章（卷章结构以全书大纲为准，只读）
- `C_missing` = `C_planned − C_outlined`。章号从 1 连续覆盖，因此**最早缺失章** `start` = 从 1 起第一个不在 `C_outlined` 的已规划章号
- `earliest_arc` = 包含 `start` 的 arc（取自全书大纲结构 `.narracat/data/outline/outline-structure.json` 的 volumes[].arc_list，由宿主写进交接材料，含 arc_id / chapter_start / chapter_end / 三件套 / payoff_beats）
- 后续 arc 取法（arc 区间连续不留缝）：`chapter_start` = 当前 arc 的 `chapter_end + 1` 的 arc；没有即已到规划末尾

**输出三分支：**

| 条件 | 判定 |
|---|---|
| `C_missing ≠ ∅` | 补纲：从 `start` 起按叙事断点窗口推进（§3） |
| `C_missing == ∅` 且 `C_planned` 章数 < 预计总章数（作品设置） | 展开下一卷：后面的卷只有卷梗概（§4） |
| `C_missing == ∅` 且规划已覆盖预计总章数 | 全部完成 |

**叙事断点（窗口收口点）：** 派发以章为粒度的窗口 `[start, target]`，`target` 是从 `start` 起最近的一个**叙事断点**——剧情上自然成段的收口章。断点取自结构化大纲数据（书级 `storylines` 的 `entry_chapter` / `planned_payoff_chapter`、伏笔注册表的 `planted_chapter` / `target_reveal` 章号锚点、arc 的 payoff_beats 兑现点、arc 的 `chapter_end`=arc 闭合），每个断点带一句剧情理由（如「SL-02 入场」「F-MED-05 兑现点」「V01-A02 闭合」）。collaborative 档的断点候选由 outline-architect 读结构化大纲推算并提供，宿主核对各候选满足最小前瞻窗口、不超过已规划末章后，用问答卡请作者选；auto 档不产候选，`target` 由宿主按 §3 的机械规则直接取 arc 闭合章。

**约束：**

- **起点固定：** 窗口必须从 `start`（最早缺失章）开始，不允许用户自选起点（远距离跳跃补纲禁止）；用户只决定窗口产到哪个断点（§3）
- **最小前瞻窗口 = 5 章：** 窗口跨度（`target - start + 1`）需 ≥ 5 章，以保证窗口内伏笔埋设-兑现的编排成立；断点不足此窗口时顺延到下一个满足的断点。已到规划末尾（无后续 arc）时取最后一个断点，跨度不足 5 章亦可——此时窗口就是剩余全部章。**例外：** 作者在对话里亲口给了范围时以作者为准（短于 5 章也照做，Agent 在回复里提一句），宿主核对原话里有这个章号
- 区间已局部细化（窗口内已有部分章纲）时，已有章纲的章不在提交范围内：从 `start` 起依次交还没有章纲的章（§3 不覆盖）

## §3 叙事断点窗口批次与不覆盖

**窗口选取：**

- **手动模式（collaborative）：** outline-architect 依结构化大纲提供从 `start` 起的若干「产到第 N 章（断点理由）」候选（按章号升序、各满足最小前瞻窗口）；主会话把候选交宿主（`project_outline_submit` layer=window），宿主用问答卡以人读中文标题（如「产到第 52 章 · 苏见第一次渡河」）请作者选定一个 `target`，另附「暂不细化」。断点理由是人读说明，不带编号。作者在对话里已经给了范围时不弹这张卡（见 §2 例外）。
- **auto 模式：** 不询问，也**不派发断点候选**——`target` 由宿主按 arc 闭合章机械算出，零 LLM 裁量：

  1. `target` = `earliest_arc.chapter_end`（arc 闭合即引擎设计的剧情收口点：arc 的 `irreversible_change` 在此落地）
  2. 若 `target - start + 1 < 5`（最小前瞻窗口，§2），顺延到下一个 arc 的 `chapter_end`（后续 arc 取法见 §2），重复直至跨度 ≥ 5 章
  3. 无后续 arc（已到规划末尾）→ 取当前 `target`，跨度不足 5 章亦可

  同一项目状态重复跑本命令，铺纲范围必然一致；单次范围由宿主的细化窗口上限封顶（一次最多 40 章，与 arc 长短无关），成本可预算。auto 档不消费 payoff_beat 兑现点这类更细的断点——确定性优先于断点精细度。

**单窗口即收口（硬边界）：** 一次命令运行只推进 `[start, target]` 这一个窗口。窗口内全部段提交完成后直接进入完成输出——不重新计算最早缺失章、不取下一个 arc、不追加新窗口；越过 `target` 的任何章一律留给作者下次运行本命令。auto 档同样受此约束（auto 免掉的是询问，不是窗口边界）。宿主拦住越过终点的提交，运行结束时对账窗口做没做满，没做满在任务回执里写明还差哪些章。

**派发与提交：**

- 选定 `target` 后，窗口 `[start, target]` 逐批派发 outline-architect（阶段二 Envelope 传章区间与所在段的梗概；立项卡、篇幅与设定目录由宿主经岗位交接包附上），由其自行调 `project_outline_submit`（layer=chapters）提交；**一次提交最多 10 章（宿主核对，与段长、分不分段无关），窗口更长时拆成多次提交**，分批提交便于失败隔离与重试。每批首章须是当时的最早缺失章、依次接上
- **不覆盖：** 已有章纲 json 的章，宿主不收进补纲提交（引擎新交章纲也退回已有的章）。修改已有章纲不在补纲流程内：Agent 用 `project_outline_submit`（layer="chapter_edit"）按字段改、核对读到的旧值，作者在大纲页的章纲卡上改第一档——两边是同一个章纲入口

**失败处理：**

- 某段提交次数用完（宿主按提交键计数）→ 保留已成功段的产物不回滚，宿主问作者再改一次或先停下
- 中断后重跑由 §1 扫描自愈，下次从新的 `start` 重新计算窗口，不需要人工对账

## §4 阶段一范围：逐卷展开（ADR-0088 附记）

- **开书：** 不分篇幅档，阶段一只提交书级（全书梗概 `synopsis` 与谜底 `mysteries`、引擎字段、全书级的线与伏笔、各卷梗概 `volume_plan`）＋ 第一卷（含完整 arc_list、每个 arc 的段梗概与这一卷自己的线与伏笔）。后面的卷只有卷梗概，引擎按它把这些卷渲染为待展开；远期伏笔的 `target_reveal` 可用「vol-08」形态的卷级粗锚点。
- **展开下一卷：** §2 判定为补卷（已规划的章都有章纲、规划还没到预计总章数）时，宿主在大纲现状与岗位交接包里给出这一卷的卷梗概（交接包另附全书梗概与谜底）；派发阶段一·展开下一卷 Envelope——按卷梗概与已写的内容产这一卷的卷级 + arc_list（每个 arc 带段梗概），用 `project_outline_submit`（layer="volume"）提交，payload 带这一卷的 volumes，可另带这一卷新增的 storylines / foreshadowing_registry（新 id 追加，库内已有的以库内为准）与修订后的 volume_plan（按卷号合并）；书级其余字段与已有卷不动，由引擎按卷号合并进大纲结构文件并扩展 structure 同步。
- **collaborative 新建（两段制）：** 书级段（layer="book"）提交全书梗概与谜底 + 引擎字段 + 全书级的线与伏笔 + 各卷梗概，引擎写进大纲结构文件（`.narracat/data/outline/outline-structure.json`，全书大纲与卷纲只存这一份），没展开的卷按卷梗概标待展开，宿主问作者确认骨架；作者确认后展开第一卷（layer="volume"），书级以库内为准不覆盖（作者确认窗口内的直接修改自然保留）。每展开一卷宿主问一次结构确认，确认后才细化这一卷的章纲。协作档书级没展开时宿主不收 full。整组替换形态（layer="volumes" / "full"）只用于整体重排；会让既有卷消失时宿主先问作者，作者同意才删。
- **auto 新建：** 一次提交书级（含全书梗概、谜底、各卷梗概）与第一卷（layer="full"，volumes 只带第一卷）；后面的卷同样写到之前再展开。
- **全书梗概与谜底改动：** 分卷展开后整份重交改了已有的全书梗概或谜底，协作档宿主先问作者（不同意就退回），自动档照改、回执提醒写明改了什么。
- **书级待展开判定：** 全书大纲结构（`.narracat/data/outline/outline-structure.json`）存在且 `volumes` 为空数组。该判定必须先于修改与补卷判定——先于修改是防带指令重跑绕过书级确认门（指令应作为骨架调整意见），先于补卷是防「已规划 0 章 < 预计总章数」误命中 §2 补卷条件。

## 引用规则

- 命令/agent 文件引用本契约必须带 `<插件根目录>/` 前缀——运行时 cwd 是用户项目，裸相对路径读不到 plugin 内文件
- 命令文件不复制本契约的算法步骤、参数定义、约束条件，只保留：调用时机、场景特化、输出消费分支，以及核心安全约束的一句话重复（「起点固定」「最小前瞻窗口」「不覆盖」）
