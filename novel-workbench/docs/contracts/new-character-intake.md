# 契约：写作期新角色处置 + 角色档案渐进深化

> 共享契约 SSOT（角色随剧情渐进生长，不在立项期一次产全）。消费方（引用须带 <插件根目录>/` 前缀）：
> - 规划方法：大纲规划期 outline-architect 引用未建档角色时处置
> - 写章方法：写作期 chapter-writer 申报了未建档角色时处置
> - 设定方法 / `agents/world-curator.md`：建档 / 深化角色时标注完善度阶段

当 subagent 在大纲 / 正文里引用一个**已建档角色清单与候选清单都没有**的名字时，主会话按本契约处置——不打断创作流、不强制完整设定、不问作者。

## 〇、角色档案完善度阶段（stub→sketch→full）

人物身份可带 `profile_stage`（选填，设定提交时随结构化字段交），标注档案当前完善度——作者随时可让 `/narracat:world` 深化一级：

| 阶段 | 含义 | 至少覆盖 |
|---|---|---|
| `stub` | 写作期就地拉起的轻量建档 | 名字 + 一两句已知信息，其余维度「（留白）」 |
| `sketch` | 关键维度成形、可支撑出场 | 身份 / 欲望 / 核心矛盾 / 与主角关系（world-guided.md 角色 6 维度过半） |
| `full` | 全维度完整 | world-guided.md 角色 6 维度全覆盖，无「（留白）」 |

人物身份在 `.narracat/data/bible/characters/{name}.json`（编号、名字、别名、完善度等），档案正文 `bible/characters/{name}.md` 只有设定文字。缺 `profile_stage` 按 `full` 兼容（立项期既有档案）。深化只升不降，UID 与 name 原样保留。

## 一、识别新角色

判定一个被引用的名字属于哪一类：

1. `.narracat/data/bible/characters/*.json` 里已有同名人物（或某人的 `aliases` 里有该名）→ **已建档**，直接放行，无需处置。
2. 同一名字此前已经由 `project_outline_submit`（`layer: 'character'`）登记为候选（本版本没有独立的候选清单工具）→ **已是候选**，直接放行：规划期章纲让他作视角人物或出场角色时，宿主入库前按他登记时的备注与关系建简档；写作期出场时再建档。建档沿用他的预留 UID，建档后宿主自动把他移出候选。
3. 都不在 → **新角色**，进入第二节处置。

## 二、新角色处置（先判重要度 → 龙套跳过 / 次要入候选 / 重要建简档）

### 先判重要度

每个新名字先归一档，看两点：①是否在本章 / 本卷大纲被规划过（被规划=有意安排，至少「次要」，多半「重要」）；②正文里的戏份——推动剧情、与主角形成持续关系、明显还会回来 → **重要**；会再出现但不牵动主线 → **次要**；只在背景里报个名 / 办个功能就退场 → **龙套**。

`write` 来源才做龙套判定；`plan` 来源的新角色是有意写进大纲的，不当龙套，至少「次要」。

三种归宿（两档都不问作者，作者在设定页随时能改、能删）：

- **龙套** —— 一次性、纯功能性背景。**不登记、不建档**，正文里照常写（无需 UID）；下次再出现会作为新名字重新判定。
- **次要** —— 入候选池，本次不建档、不写正文设定。
- **重要** —— 建简档（`stub`）：调 `project_settings_submit`（`kind: character`，`op: create`，`profile_stage: stub`），档案以「# 名字」开头，正文与申报里已知的写上、其余写「（留白）」；身份（UID）与文件位置由宿主定。需要完整设定时再深化（见第〇节阶梯）。

新名字其实是已建档角色的另一个叫法时，不新建、不进候选：用 `project_settings_submit` 在那个角色档案的别名里补上。

**只有称呼、还没起名的人物**（如「剑庐师叔」「她身边的沉默旧部」）与新名字同样处置：判重要度与执行都一样，下文的 `{名字}` 用称呼代替名字；留作候选时 `name` 以称呼登记，以后起了名、建档时把这个称呼补登为别名。

### 谁来执行

- **大纲规划期（`plan`）**：每个新人物交宿主的大纲提交程序（`project_outline_submit`，`layer: character`，附名字或称呼、重要度、首次出场章）。次要的由宿主登记进候选、给出身份，要他上场就照常写进章纲的视角人物或出场角色（宿主入库前给他建简档）；重要的宿主交回 `create`，主会话照提示建简档（大纲岗位手上没有设定提交工具：这批章纲的视角人物与出场角色先不写他，回执里写明是谁、要什么，由主会话建档）；照结果里的身份与提示办。
- **写作期（`write`）**：主会话在提交本章前逐个处置——次要调 `project_outline_submit`（`layer: character`，`payload: {name: "{名字}", proposed_chapter: {章号，如有}, importance: "minor", source: "write"}`），重要按上面建简档。

## 三、建档后的级联分析（按时间插入点路由）

建简档并落盘后，按角色相对**已写章**（`manuscript/` 下有正文的章）的时间插入点判定级联深度，组织成 CascadeImpactReport（`change_kind=character_added`）：

- **forward（纯前向）**：proposed_chapter 在最后写完的一章之后、且角色此前不涉及任何已写章 → 仅建档，无级联（`insertion_point=forward`，`has_impact=false`，不读已写章）。
- **backward（向后出场）**：角色从某未来章起出场，已写章无需回溯 → 后续大纲与写作自然纳入，不动已写章（`insertion_point=backward`，已写章无 affected）。
- **retroactive（追溯）**：角色其实早该在某些已写章出现 → `insertion_point=retroactive`，逐章 Read 相关已写章，affected_chapters 列出需 memory-keeper 回填 facts/关系的章；正文有硬冲突的标 `impact_level=critical` 并建议 `/narracat:rewrite <章号>`，软冲突标 continuity 提示。回填不自动改正文。

无级联（forward/backward）一行带过；retroactive 有 affected 时按 `change_kind=chapter_rewrite` 同款表格呈现 | 章节 | 影响级别 | 问题 | 建议 |，由作者决定回填/重写时机。

## 四、纪律

- 候选角色不入 facts / character_cards（无设定可入），只在候选池登记（实体登记表里带预留人物编号的条目），与已出场角色的记忆体系隔离。
- 龙套不进候选池、不铸 UID，只作为正文文字存在；重要度只在「次要 / 重要」两档区分，决定写完正文是否提醒建档——写完只提醒「重要」候选。
- stub 建档同样是一份人物身份 json 加一份档案正文 md，一律经宿主设定提交程序定身份（按名字或别名复用候选 UID，否则宿主铸号）。
- 一名一处置；疑似已建档角色的别名又拿不准时，按新人物处置，在完成汇报里说一句，由作者在设定页合并。
